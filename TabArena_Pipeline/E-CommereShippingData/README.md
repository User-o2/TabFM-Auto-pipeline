# E-CommereShippingData — final pipeline

## What it does

The pipeline throws away almost the entire table. Analysis of the 7332 training rows showed that
only three of the ten raw columns carry signal, and that they carry it as a piecewise-constant
structure rather than as a smooth function: a deterministic region (`Discount_offered > 10`, or
`2000 < Weight_in_gms < 4000`, or `Weight_in_gms > 6000`) covers ~26% of rows and is essentially
100% positive; among the rest, very light parcels (`Weight_in_gms <= 2000`) that are also cheap
(`Cost_of_the_Product <= 200`) are ~85% positive, a narrow weight band just above 4000 g behaves
differently from the bulk, and everything else sits near the base rate. So `engineer` collapses
weight and discount into one five-level categorical `seg` column (`det` / `pocket` / `lite` /
`near` / `heavy`) and keeps exactly one numeric column, `Cost_of_the_Product`, which still tilts
the heavy segment. Per-segment cross-validated logistic regressions over all ten raw columns came
out at chance (0.49–0.50 AUC), which is why no further columns were added.

TabFM is the only predictor: it does in-context learning over the two-column training table.
`preprocess` and `postprocess` are identity. The remaining gains came from how TabFM estimates
that small model rather than from features — `norm_methods=['none']` and `average_logits=False`
in `TABFM_KWARGS`, and `sample` returning six independent 90% subsamples of the training rows, so
the judge's 8-member ensemble is run six times over different contexts and averaged (48 members).
Validation used repeated stratified 5-fold (3 repeats, 15 splits) so each fold's context is close
in size to what the final fits on and paired comparisons are less partition-noisy. Metric is
`1 - AUC`, lower is better; the search moved it from 0.2524 (raw columns, same folds) to 0.2450.

## build.sh

There is nothing to build. `final/build.sh` prints one line and exits 0. The pipeline reads no
file from disk — every feature is computed from the dataframes the judge passes to the hooks — and
no helper script or cache was produced during the run, so there is no `final/build/` directory.
Zero disk, instant.

```
cd <this workspace> && bash final/build.sh && python final/run.py
```

## Things a reader could get wrong

- **`seg` must stay plain `object` dtype.** `_add` builds it with `dtype=object` on purpose. An
  earlier version used a pandas string dtype, which is pyarrow-backed here; the judge host has no
  pyarrow, so the column could not be unpickled across the hook boundary and the evaluation
  errored out. Do not "clean this up" to `astype("string")`.
- **The segment boundaries are exact and were tuned.** `w > 2000 & w < 4000` (strict on both
  sides), `w <= 2000` for lite, `4000 <= w <= 4200` for near. Widening `near` from 4100 to 4200
  alone was worth ~0.001 AUC. They are not round numbers by accident.
- **The raw `Weight_in_gms` column is deliberately absent.** Adding it back on top of `seg` made
  things clearly worse (0.2495 vs 0.2467); TabFM ends up smoothing across boundaries the code
  already encodes. Conversely, masking `Cost_of_the_Product` to only the segments where a logistic
  reference wanted it also hurt — TabFM wants that column raw and unconditioned.
- **`sample` returning a list of index arrays means bagging, not subsetting.** Six draws is a
  wall-clock cost of 6× one TabFM pass; dropping to 3 costs ~0.0005 AUC if runtime matters.
- **The competition data is not regenerated by anything here.** It comes from the TabArena cache
  (`~/.cache/tabarena`, dataset `E-CommereShippingData`, 9 folds per `final/config.yaml`) and the
  judge loads it. `final/run.py` will fail if that cache is absent.
- `final/run.py` refuses to run if the workspace `pipeline.py` differs from `final/pipeline.py`;
  they are identical as shipped.
